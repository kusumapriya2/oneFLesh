1.2 Document Purpose
This Business Requirements Document (BRD) and Software Requirements Specification (SRS) defines all functional, non-functional, security, and technical requirements for the Covenant Matrimony platform — a pastor-led matrimonial web and mobile application exclusively serving Reformed churches across India.

This document is the single source of truth for the product development team, covering:
All application modules and their detailed functional requirements
User roles, permissions, and access control
Application security architecture and compliance requirements
API specifications and third-party integrations
Non-functional requirements: performance, scalability, availability
Agile delivery structure: epics, user stories, acceptance criteria

1.3 Scope
The platform consists of five primary components:
Web Application (React.js) — primary interface for pastors and platform administrators
Mobile Application (React Native) — iOS and Android for pastors on the go
RESTful Backend API (Node.js / Django REST Framework)
PostgreSQL relational database with encrypted PII columns
AI Matching Engine — powered by Claude API (Anthropic)

1.4 Out of Scope
Direct candidate (bride/groom) access to profiles — all access is pastor-mediated
Integration with government identity verification systems (Phase 2)
Payment gateway for Phase 1 free tier (Phase 2)
Video calling feature within platform (WhatsApp / Zoom links used instead)

3. Application Security Requirements
NOTE: Security is treated as a first-class concern. All requirements in this section are MANDATORY and non-negotiable for production launch.

3.1 Authentication
3.1.1 Login Methods
The platform shall support the following authentication mechanisms:
Email + Password (primary method for Pastor and Admin accounts)
OTP via SMS (Twilio) — mandatory for first-time login and password reset
Google OAuth 2.0 SSO — optional convenience login for pastors
Magic link via email — optional for password-less access

3.1.2 Password Policy
Policy Rule
Requirement
Minimum length
12 characters
Complexity
Must contain uppercase, lowercase, number, and special character
History
Last 5 passwords may not be reused
Expiry
Passwords expire every 180 days; users prompted to change
Failed attempts lockout
Account locked after 5 consecutive failed attempts
Lockout duration
30 minutes; unlockable via email OTP
Storage
Bcrypt with cost factor 12 — NEVER plaintext or MD5/SHA1

3.1.3 Multi-Factor Authentication (MFA)
MFA is mandatory for all Pastor and Admin roles
Supported methods: TOTP (Google Authenticator / Authy), SMS OTP
Backup codes: 8 single-use recovery codes generated at setup
MFA bypass is NOT permitted; no admin override in production

3.2 Authorisation &amp; Access Control
3.2.1 Role-Based Access Control (RBAC)
The system shall implement RBAC with the following principles:
Least-privilege: all roles default to minimal permissions
Attribute-Based Access Control (ABAC) on profiles: a pastor can only edit profiles belonging to their verified church
Row-level security enforced at database layer (PostgreSQL RLS policies)
All API endpoints validate JWT claims for role and church_id on every request

3.2.2 Session Management

3.3 Data Security &amp; Privacy
3.3.1 Data Classification
Classification
Data Type
Protection

Passwords, private keys, OTP secrets

Platform statistics, public vendor descriptions

3.3.2 Encryption Standards
All data in transit: TLS 1.3 minimum (TLS 1.0 / 1.1 disabled)
All data at rest: AES-256-GCM for database and file storage
PII columns (phone, email, Aadhaar if collected): column-level encryption via pgcrypto
File uploads (photos): encrypted server-side in S3 with SSE-S3
Backup files: encrypted with separate KMS key

3.3.3 Data Residency &amp; Compliance
All user data stored on AWS ap-south-1 (Mumbai) region — Indian data residency
Compliance with IT Act 2000, DPDP Act 2023 (India)
Right to erasure: user account and all PII must be permanently deletable within 30 days of request
Audit log retention: 2 years minimum, stored separately from application data

3.4 API Security
Security Control
Implementation
Authentication
JWT Bearer token on every authenticated endpoint
Rate limiting
100 req/min per IP; 1000 req/min per authenticated user
Input validation
Zod / Pydantic schema validation on all request bodies
SQL injection prevention
Parameterised queries only; no string concatenation in queries
XSS prevention
Content-Security-Policy headers; DOMPurify on all rendered HTML
CSRF protection
SameSite=Strict cookies; CSRF token on state-changing requests
CORS policy
Whitelist: app domain, admin domain only — no wildcard origins
API versioning
All endpoints prefixed /api/v1/ — breaking changes require new version
Sensitive data in URLs
Never — profile IDs are UUIDs, no PII in query parameters
HTTPS enforcement
HSTS header with max-age=31536000; includeSubDomains; preload

3.5 Infrastructure Security
Hosting: AWS (Mumbai region) with VPC isolation — RDS not internet-accessible
WAF: AWS WAF with OWASP Core Rule Set enabled on CloudFront
Penetration testing: mandatory before launch, annually thereafter
Vulnerability scanning: OWASP ZAP in CI/CD pipeline on every release
Secrets management: AWS Secrets Manager — no credentials in source code or env files
Container security: Docker images scanned via Trivy in CI/CD pipeline
Dependency auditing: npm audit / pip audit run on every build
Incident response plan: documented SLA — P1 (breach) response within 1 hour
